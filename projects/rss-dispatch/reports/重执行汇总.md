## 重要观察

1. 两个独立浏览器会话可完成管理员与普通用户的权限变更验证；此前同一 IAB 浏览器的多个标签页共享认证状态，不能作为双账号隔离证据，详见 [隔离观察](../artifacts/TC-RSS-FL-AUTH-02/iab-tab-isolation.dom.json)。
2. `RSS-AUTO-MENU-A` 的新增操作返回“保存成功”，但刷新后菜单树不包含该菜单。应由产品/API 侧核查新增菜单请求、父菜单编码和保存响应的 `statusCode`/`isSuccess`，不能仅凭成功提示判定 PASS。
3. 测试期间创建的 `RSS-AUTO-ADMIN`、`RSS-AUTO-USER`、`RSS-AUTO-ADMIN-ROLE`、`RSS-AUTO-FLOW-ROLE` 均已删除；外部系统配置未修改。
4. 环境中原有字典 `001-10 / CS / 系统` 未删除，因为系统类型字典按文档不可删除，且不是本轮创建的数据。

## 文档仍欠缺的执行条件

- 未提供可执行的 API 健康检查 URL、前后端版本对应关系及网络响应断言清单。
- 未提供数据库/Redis/日志的只读核验连接、脱敏规则和查询模板；本轮主要完成 UI、路由和提示验证。
- 未提供 `sa` 是否应存在于用户表的环境约束。当前实际环境是 `sa` 可登录且显示为超级管理员，但用户表查询为 0 条，导致 FL-AUTH-06 无法完成。
- 未提供 HTTP 403/600、业务 600、旧 token 注销和 sessionStorage 隔离的可复现 API 测试入口，因此 FL-AUTH-04 只完成无会话重定向子项。
- 菜单新增的成功响应契约不足：需要明确保存接口如何同时判断 `statusCode` 与 `isSuccess`，以及新增后查询一致性要求。
