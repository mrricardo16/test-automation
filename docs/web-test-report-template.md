# Web 测试报告统一生成模板

## 1. 适用范围

本模板同时适用于功能依据和流程依据。每份依据文档生成两份报告：

| 依据类型 | 完整报告 | 问题反馈报告 |
|---|---|---|
| 功能 | `功能依据名称_完整测试用例报告.md` | `功能依据名称_问题反馈报告.md` |
| 流程 | `流程依据名称_完整测试用例报告.md` | `流程依据名称_问题反馈报告.md` |

依据名称需要去除 `.md` 和末尾括号编号。例如：

```text
功能_02_Web管理端_系统管理(4).md
→ 功能_02_Web管理端_系统管理_完整测试用例报告.md
→ 功能_02_Web管理端_系统管理_问题反馈报告.md

流程_01_权限与登录(3).md
→ 流程_01_权限与登录_完整测试用例报告.md
→ 流程_01_权限与登录_问题反馈报告.md
```

## 2. 完整报告统一结构

功能报告和流程报告使用相同的五段式结构，只替换“功能/流程”对象名称：

```text
# <对象名称>测试报告

## 1. 测试基本信息
## 2. 已执行<功能/流程>结果
## 3. <功能/流程>条目状态
## 4. <功能/流程>测试结论
## 5. 测试实现与证据
```

### 2.1 测试基本信息

必须包含：

| 字段 | 生成来源 |
|---|---|
| 测试依据 | 输入的原始功能/流程 Markdown 文件名 |
| 测试地址 | 本次实际执行的 Web 地址 |
| 测试账号 | 账号名可以写；密码、Token、Cookie 不得写入 |
| 执行日期 | 执行批次日期，不手工伪造 |
| 执行方式 | Playwright、浏览器、上下文和必要的人工验证边界 |
| 数据处置 | 创建了什么测试数据、是否清理、清理结果 |
| 产品代码 | 固定说明未修改被测产品源码 |

### 2.2 已执行结果表

结果表必须使用以下列顺序，图片证据始终位于最右侧：

| 用例/流程 | TestCaseId | 状态 | 实际验证 | 图片示例 |
|---|---|---|---|---|
| `<行为或步骤>` | `<唯一 TestCaseId>` | `<状态>` | `<真实观察>` | `<报告目录内图片缩略图及原图链接>` |

规则：

- 每一行至少关联一个已登记的 TestCaseId；多个 TestCaseId 只有在同一连续行为且证据不可分离时才允许合并；
- `实际验证` 只能填写真实观察，不得用预期结果代替；
- 每行都要有图片示例；没有可用图片时必须标记 `MANUAL`、`BLOCKED` 或说明证据缺失原因；
- 图片缩略图可以使用 HTML，但 `href` 和 `src` 必须是报告目录内的相对路径；
- 不建立独立“人工复审图片证据”章节，人工复审通过右侧图片列完成。

### 2.2.1 用例粒度与复合用例

完整测试用例报告必须同时呈现 `ATOMIC` 原子用例和 `COMPOSITE` 复合用例；`ScenarioSuite` 只用于组织生命周期和聚合覆盖，不直接产生执行状态。

- 一个可独立执行、独立判定、独立取证的场景必须独立生成一个 TestCaseId 和一行结果；不得把“精确、模糊、无匹配、分页”合并为一条查询用例。
- 复合用例只允许一个主要业务目标，必须记录操作序列、每步预期、状态变化、主要断言、后置条件、跨步骤不变量和清理验证。
- 功能报告必须按适用性评估并记录 `新增→查询`、`修改→查询`、`删除→查询`、`删除→重新新增`、`删除→再次删除`、`禁用→登录` 等跨操作场景。
- 需求未定义的复合行为（例如删除后能否复用同名唯一属性）必须记录为 `EXPECTATION_GAP` 或 `SKIPPED`，不得根据实际运行行为猜写 Expected。
- 多个独立业务目标拼接成一条长链路属于 Mega Case，必须拆分为多个 TestCase，再由 ScenarioSuite 聚合。

### 2.3 条目状态表

功能报告使用“功能条目状态”，流程报告使用“流程条目状态”，结构一致：

| 功能/流程条目 | 状态 | 未执行原因 |
|---|---|---|
| `<依据条目 ID> <条目名称>` | `<状态>` | `<未执行原因；PASS 可写已完成说明>` |

条目状态必须来自真实执行结果，不能因为某个子用例通过就把整个条目标记为 PASS。条目包含多个分支时，以未完成的最高影响分支为准，并在原因中说明已完成和未完成部分。

### 2.4 测试结论

结论由结果表和条目状态表派生，必须说明：

- PASS、FAIL、ERROR、BLOCKED、MANUAL、SKIPPED 数量；
- 已真实通过的范围；
- 未执行或只能人工验证的范围；
- ERROR 是否为脚本/环境问题，不能自动等同产品缺陷；
- SKIPPED 不等同 PASS；
- 测试数据清理结果和仍需开发确认的事项。

### 2.5 测试实现与证据

必须关联：

- TestCase 记录路径；
- Playwright 自动化脚本路径；
- 截图、Trace、网络摘要、页面错误和日志路径；
- 证据路径必须使用仓库相对路径或项目内约定的相对路径；
- 不写入本机绝对路径、密码、Token、Cookie 或敏感响应值。

## 3. 功能报告覆盖规则

功能报告至少覆盖以下场景：

- 查询：空条件、精确、模糊、无匹配、前后空格、特殊字符、非法字符、长度边界、多条件、分页、重置和重复查询；
- 新增：正常新增、必填、格式、长度边界、重复属性、重复提交、取消、保存失败、保存后查询和清理；
- 修改：正常修改、重复属性、非法输入、长度边界、对象不存在、并发修改和刷新持久化；
- 删除：单条、批量、重复删除、部分失败、删除后查询和删除后再次操作；
- 权限关系：角色关联、菜单/按钮可见性、权限变更、普通账号与 SA 差异；
- 状态恢复：启用/禁用、失败回滚、异常提示和刷新后状态。

## 4. 流程报告覆盖规则

流程报告在功能覆盖规则基础上，额外覆盖：

- 跨步骤前置条件和后置条件；
- 账号创建、授权、登录、禁用、恢复、删除和清理生命周期；
- 独立浏览器上下文及会话影响；
- 权限变更前后、刷新前后和重新登录后的对照；
- 多端并存、并发和会话失效；
- Token/接口、授权文件、系统时间等不属于当前 Web 页面能力的边界。

无法通过当前 Web 页面安全验证的内容必须记录为 `SKIPPED`、`BLOCKED` 或 `MANUAL`，不得虚构 PASS。

## 5. 问题反馈报告生成规则

问题反馈报告从完整报告自动提取以下结果：

- `FAIL`：真实产品结果与预期不一致；
- `ERROR`：测试脚本、定位、浏览器或执行基础设施错误；
- `BLOCKED`：缺少前置条件或安全边界不允许执行；
- `MANUAL`：只能人工验证的行为；
- `SKIPPED`：只有在对开发或环境负责人有反馈价值时才提取。

问题报告不得复制无关 PASS 用例。每条问题必须包含：

```text
问题/场景、TestCaseId、状态、分类、严重程度、预期、实际、证据、图片示例
```

首次失败、错误或阻塞证据必须保留；重试通过不能覆盖首次异常。

## 6. 生成前检查

生成报告前必须确认：

1. 测试依据文件可读且为 UTF-8；
2. 每个正式自动化 TestCase 已先登记唯一 TestCaseId；
3. 测试账号和测试数据满足真实业务约束；
4. 测试地址、浏览器、执行批次和数据清理策略已确定；
5. 图片证据目录已经创建；
6. 不会把密码、Token、Cookie 或敏感响应值写入任何报告。

## 7. 生成后治理检查

`scripts/platform/report-governance.mjs` 必须校验：

- 模板文件的统一章节和字段；
- 本地存在时四份报告的命名、结构和合法状态；
- 结果表右侧 `图片示例` 列；
- 图片路径为报告目录内相对路径且文件存在；
- 问题报告没有 PASS 问题行；
- UTF-8、无绝对路径、无独立图片复审章节和无敏感信息。

主干保存本模板、TestCase 规则和治理脚本；实际运行报告、截图、Trace 和其他运行产物保留在项目本地的 `projects/<project-slug>/` 目录。
