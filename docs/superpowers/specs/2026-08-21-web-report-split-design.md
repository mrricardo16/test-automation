# Web 测试报告拆分设计

## 目标

将每份测试依据文档拆分为两类交付物，并统一生成规则：一份面向测试评审的完整测试用例报告，一份面向开发反馈的问题报告。两份功能依据和流程依据分别执行，因此一个测试任务共产出四份报告。

## 交付物结构

| 测试依据 | 完整测试用例报告 | 问题反馈报告 |
|---|---|---|
| `功能_02_Web管理端_系统管理(4).md` | `功能_02_Web管理端_系统管理_完整测试用例报告.md` | `功能_02_Web管理端_系统管理_问题反馈报告.md` |
| `流程_01_权限与登录(3).md` | `流程_01_权限与登录_完整测试用例报告.md` | `流程_01_权限与登录_问题反馈报告.md` |

文件名使用简洁中文，不保留依据文件名中的括号编号；报告正文保留原始依据文件名，保证可追溯。

## 完整测试用例报告

完整报告面向测试工程师和人工复审人员，必须包含：

- 测试依据、环境、账号边界、浏览器、执行批次和数据清理说明；
- 需求/流程条目到 TestCaseId 的追踪矩阵；
- 每个用例的前置条件、测试数据、操作步骤、预期结果、实际结果和状态；
- 右侧 `图片示例` 列，图片缩略图可点击打开原图；
- PASS、FAIL、ERROR、BLOCKED、MANUAL、SKIPPED 的统计和限制说明；
- 每条正式自动化用例对应的 TestCase 记录和证据路径。

功能用例设计至少从以下维度展开：

- 查询：空条件、精确、模糊、无匹配、前后空格、特殊字符、非法字符、长度边界、多条件组合、分页、重置、重复查询；
- 新增：正常新增、必填项、格式校验、长度边界、重复属性、重复点击、取消、保存失败、保存后查询、数据清理；
- 修改：正常修改、重复属性、非法输入、长度边界、对象不存在、并发修改、刷新后持久化；
- 删除：单条、批量、重复删除、部分失败、删除后查询、删除后再次操作；
- 权限和关系：角色关联、权限变更、菜单/按钮可见性、普通账号与 SA 差异；
- 状态和恢复：启用/禁用、登录态、失败回滚、异常提示和刷新后状态。

流程用例在上述维度之外，必须覆盖跨步骤状态、账号生命周期、独立浏览器上下文、会话影响和恢复动作；无法通过当前 Web 页面可靠验证的接口、Token、并发或主机级行为必须明确标记范围外或 SKIPPED/BLOCKED。

## 问题反馈报告

问题报告只收集需要开发或环境负责人处理的项目，不复制所有 PASS 用例。每条反馈必须保留：

- 问题编号、关联 TestCaseId、依据条目和复现前置条件；
- 预期结果与实际结果；
- 分类：产品失败、测试脚本错误、环境错误、定位错误、数据准备失败或执行阻塞；
- 严重程度、复现概率、影响范围和建议责任方；
- 图片、Trace、网络摘要、日志或错误栈证据；
- 当前状态和是否需要重新执行。

FAIL 表示真实产品结果与预期不一致；ERROR 表示自动化、定位、浏览器或执行基础设施错误；BLOCKED 表示前置条件缺失或安全边界不允许继续；MANUAL 表示必须人工验证；SKIPPED 仅在未执行且原因对开发/环境有反馈价值时进入问题报告，否则只在完整报告中说明。

## 安全和证据约束

- 密码、Token、Cookie、API Key 和敏感响应值只能通过运行时变量使用，不能进入报告、TestCase、截图说明或日志摘要；
- 图片证据存放在报告目录下的 `图片证据/`，报告使用相对路径；
- 失败和错误证据必须保留，不能用后续重试覆盖首次失败；
- 只修改自动化测试仓库，不修改被测产品源码；
- 所有 Markdown、TypeScript、JSON 和文本文件保持 UTF-8。

## 验收标准

1. 功能依据和流程依据各有一份完整报告和一份问题反馈报告。
2. 完整报告的每个正式用例都有唯一 TestCaseId、预期/实际结果、状态和证据引用。
3. 查询、新增、修改、删除和权限流程包含正常、边界、异常、重复和恢复场景。
4. 问题报告不包含无关 PASS 用例，并能区分产品失败、测试错误、环境错误和阻塞。
5. 报告治理脚本校验中文命名、图片列、相对图片路径、UTF-8 和敏感信息规则。
