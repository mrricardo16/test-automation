# DEV-TEST-HANDOFF Design

## Goal

Create a reusable Codex Skill named `dev-test-handoff` that turns readable frontend and/or backend source into a validated, source-grounded As-Built design baseline and then projects that baseline into a sanitized Markdown handoff package for black-box test agents.

This task creates the Skill only. It does not analyze a real product, execute tests, generate formal TestCases, modify product code, or create Word documentation.

## Design principles

- The only fact pipeline is `Source → As-Built → Design Validation Gate → Handoff`.
- Stage B reads the validated Stage A artifacts; it does not independently reinterpret source.
- Code evidence, supplied runtime evidence, inference, and unknowns remain distinct throughout the pipeline.
- Source inputs are read-only by default. Build, run, dependency installation, migration, database writes, and configuration changes are outside the Skill.
- The Skill accepts frontend-only, backend-only, and multi-project repositories.
- Handoff Markdown is sufficient for a source-inaccessible tester; internal paths, private symbols, credentials, and secrets are sanitized.

## Skill layout

```text
│  ├─ design-validation-gate.md
│  ├─ handoff-validation-gate.md
│  └─ security-sanitization.md
├─ templates/
│  ├─ as-built/*.md
│  └─ test-handoff/*.md
└─ scripts/
   ├─ validate_contract.py
   └─ self_test.py
```

`SKILL.md` remains a workflow guide. Detailed schemas, evidence rules, validation gates, sanitization rules, and output contracts live in references and templates. `agents/openai.yaml` provides discoverability metadata generated by the official initializer. The official Skill Creator discourages auxiliary README files, so this Skill has no README.

## Stage A: As-Built analysis

The Skill requires `output_root` and at least one of `frontend_source` or `backend_source`. It optionally accepts existing design, runtime, and test reports; scope, product name, environment notes, and excluded paths.

The source scan is staged:

1. Workspace and project inventory.
2. Entry points, routes, controllers/handlers, and API inventory.
3. Module and feature inventory.
4. Rules, validation, permissions, states, data constraints, and flows.
5. Frontend-to-backend mapping.
6. Completeness and evidence validation.

The default output is `<output_root>/as-built/` with stable files `00-index.md` through `16-design-coverage.md`. Each applicable template defines required fields and permits explicit `NOT_APPLICABLE` or `UNKNOWN` values.

Stable identifiers are assigned for modules, features, rules, flows, APIs, validations, and states. Every claim carries one of `CONFIRMED_FROM_CODE`, `CONFIRMED_FROM_RUNTIME`, `INFERRED`, or `UNKNOWN`, with source or runtime evidence where available.

## Design Validation Gate

Stage A must check that major source projects, routes, externally testable APIs, modules, mappings, rules, and unknowns are represented. Every frontend and backend API gets a mapping state (`CONFIRMED`, `PROBABLE`, or `UNMATCHED`). Every inferred or unknown claim is explicit and traceable to `15-known-unknowns.md` when applicable.

The gate writes `16-design-coverage.md`. A failed gate writes `DESIGN_BASELINE_INCOMPLETE` with Missing, Reason, and Impact. Stage B may still run only as a restricted projection marked `HANDOFF_LIMITED_BY_DESIGN_GAPS`.

## Stage B: Black-box test handoff

Stage B consumes only the validated As-Built Markdown and any explicitly approved runtime evidence. If a design gap or conflict requires source re-checking, the Skill updates Stage A first, reruns the Design Gate, and only then regenerates Handoff.

The default output is `<output_root>/test-handoff/` with `00-TEST-WORKFLOW.md` through `18-runtime-observability.md`. Handoff keeps all stable design IDs and confidence levels but removes unnecessary source implementation details and sensitive configuration.

The entry document defines the black-box Test Agent identity, reading order, coverage workflow, test-layer recommendations (`WEB_UI`, `API`, `BOTH`, `MANUAL`), status vocabulary, runtime mismatch handling, and the rule that formal TestCases are created later by the testing workflow.

Handoff includes coverage, rules, flows, validations, auth/permissions, state transitions, API contracts, test data setup/cleanup, destructive-operation safeguards, locator semantics and stability, error behavior, runtime observability, risk priority, and traceability.

## Handoff Validation Gate

The gate checks that each P0/P1 feature has an explicit applicable value for entry, expected behavior, rules, flow, validation, permission, state, API, test data, error behavior, priority, and suggested test layer. Missing applicable information is a validation failure; non-applicable items must say `NOT_APPLICABLE`, and unresolved facts must say `UNKNOWN`.

The gate verifies that Handoff IDs exactly match their As-Built source IDs, that confidence never increases during projection, and that sanitization removes secrets, credentials, private paths, and internal implementation details.

## Static self-test

`scripts/self_test.py` creates a temporary minimal fixture and checks that all references and required templates exist, that generated contract files contain required markers, that Stage B references the Stage A baseline, and that no forbidden secret/path samples are present. It does not inspect or run a real product.

`scripts/validate_contract.py` validates an already generated output root without modifying its inputs. It checks required filenames, gate markers, ID continuity, confidence vocabulary, and handoff safety markers.

## Acceptance criteria

- The Skill passes the official `quick_validate.py` check.
- The Skill is discoverable as `dev-test-handoff` and has generated `agents/openai.yaml` metadata.
- Static self-test passes using only its minimal fixture.
- The Skill contains no current product paths, credentials, customer data, or business source.
- The final repository diff contains no unrelated changes beyond this Skill and this approved design record.
- The real acceptance run against the named frontend/backend projects remains a separate next step.
