> 本文件是黑盒测试工作流的最终报告生成契约。生成器必须按本结构生成 Markdown；报告正文只展示当前正式 Fine-Grained TestCase Catalog，历史执行记录、Schema、Validator、设计审计和材料化 JSON 保存在内部资产中，不单独成为正文模块。

### 测试数据与安全原则

- 自动化写操作只允许使用测试自有或批准的隔离数据。
- 密码、Token、Cookie 和敏感响应值不写入报告。
- 写入型用例必须具备清理或状态恢复方案；清理不等于 DELETE 业务覆盖。
- 超级管理员只用于准备或清理普通用户场景所需数据，业务断言使用指定普通账号。

## 3. 细粒度正式 Catalog

主表按 `模块 → 功能 → 操作 → 业务规则 → 场景 → TestCase` 排列；同一功能的不同状态连续展示。不得按 PASS、人工、阻塞或不可执行分章。每条用例一行，pending 用例与确认预期用例共同展示，但 pending 不进入执行队列。

### 主表固定规则

主 TestCase 表固定为 9 列：`测试场景`、`TestCaseId`、`前置条件`、`测试数据`、`操作步骤`、`预期结果`、`状态`、`实际验证`、`图片示例`。图片证据必须紧跟所属用例，放在最右侧“图片示例”列；没有证据填写 `—`。不得增加聚合的“测试目标”或“测试用例设计”列。

- `测试场景`：表达一个可独立判定的业务目标。
- `TestCaseId`：使用稳定格式 `TC-<功能码>-<操作码>-<三位序号>`，同一正式 Catalog 内唯一；当前用例不得复用历史执行 ID。
- `前置条件`：只写业务前置状态。
- `测试数据`：写具体字段和值、边界或生成规则，不使用无意义占位数据。
- `操作步骤`：每条步骤编号；正文由 Renderer 按 `MAX_VISUAL_CHARS_PER_LINE=15` 主动生成真实视觉换行；最终显示为换行，不显示 `<br>` 字符串。
- `预期结果`：按语义断言编号，一条断言一行；明确数据、提示、列表、状态、权限和清理后的可观察结果。
- `状态`：只使用 `PASS`、`FAIL`、`ERROR`、`BLOCKED`、`MANUAL`、`SKIPPED`，设计阶段未执行统一为“尚未执行 / 资格”。
- `实际验证`：只填写真实执行观察；未执行为 `—`，不得用设计预期冒充实测结果。
- `图片示例`：内嵌或链接到该用例的截图；人工复审是执行行为，图片不单独拆成报告模块。

9 列主表允许超过正文宽度，必须由表格自身提供横向滚动；页面正文禁止整体横向滚动。表头不纵向拆字，TestCaseId 不换行，场景列保持自然词组换行。单元格内的 `|` 写为 `\|`，所有 Markdown 表格表头、分隔行和数据行列数必须一致。

## 7. 测试结论

说明当前正式用例数量、已确认与 pending 数量、真实执行状态、产品缺陷、测试设计问题、人工边界和剩余风险。若没有执行 Formal Run，必须明确写出“本次仅生成测试设计报告，未执行业务用例”。

## 设计生成规则

- TestCase 模型：`MODULE → FEATURE → OPERATION → BUSINESS_RULE → SCENARIO → TESTCASE`。
- 原子用例只验证一个主要业务规则；不同根因必须拆分。
- 查询必须覆盖默认加载、精确/模糊/无匹配、空值、非法字符、边界、清空重置、排序、分页、权限和查询后数据不变等适用场景。
- 新增、修改、删除必须覆盖合法、重复、空值、非法字符、长度边界、权限、状态限制和 CRUD 生命周期；组合场景包括新增后查询、修改后查询、删除后查询、删除后新增和重复提交。
- 只有同一业务规则、同一步骤和同一预期逻辑允许参数化。
- 未知 min/max 或未批准的业务预期不得猜测，生成 pending 用例并登记 Gap。
- 新细粒度用例必须生成新 TestCaseId，状态为“尚未执行”，不得继承历史结果。
- 正式 Catalog 物化到项目 `test-cases/catalog/`；生成过程产物放在项目 `outputs/`。
- 生成正式报告前必须校验 Source Catalog、Materialized Catalog、Current Effective State 和报告主 Catalog 的 TestCaseId 双向一致。
- 异常报告单独生成，只收集真实 `FAIL`、`ERROR`、`BLOCKED`、`MANUAL` 或明确需要开发确认的事项；未执行本身不是产品缺陷。
