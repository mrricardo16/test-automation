# 系统管理测试用例模板

> 用途：为系统管理、Web 页面和 Playwright 自动化测试提供统一的测试用例设计与执行记录格式。
>
> 本文件是“空白模板”，不代表任何实际执行结果。正式用例仍需先登记唯一 `TestCaseId`，再与自动化脚本建立同 ID 关联。

## 1. 主流模板字段依据

本模板吸收以下主流测试管理工具/厂商公开模板的共同字段：

- TestRail：前置条件、步骤、预期结果、优先级、估算、引用关系、附件和按步骤记录结果。
  <https://support.testrail.com/hc/en-us/articles/14927678348052-Test-case-templates>
- SmartBear：测试 ID、测试场景、假设与前置条件、测试步骤、测试数据、预期结果、实际结果、结果和备注。
  <https://smartbear.com/learn/test-management/test-case-template/>
- Atlassian：优先级、类型、前置条件、步骤与预期结果、步骤状态、用例状态和附加说明。
  <https://community.atlassian.com/forums/App-Central-articles/How-To-Build-a-Jira-Test-Case-Template-For-Your-Team/ba-p/2985515>

## 2. Excel 工作簿结构

对应 Excel 文件包含四个工作表，均保留标题行，不预填实际用例或执行结果：

### 2.1 用例设计

| 字段 | 填写要求 |
|---|---|
| TestCaseId | 唯一编号，例如 `TC-SM-USER-001`；必须与自动化测试方法/报告一致 |
| 需求/用户故事ID | 关联需求、缺陷修复单或设计文档编号 |
| 模块 | 用户管理、角色管理、菜单管理、字典管理等 |
| 功能点 | 被验证的具体功能 |
| 用例标题 | 用一句话描述验证目标 |
| 测试目标 | 说明为什么测试以及要证明什么 |
| 前置条件 | 执行前必须成立的系统状态、账号权限、数据、服务和配置；每项应可检查 |
| 测试数据 | 输入值、测试账号、数据准备方式和清理约束；禁止写入真实密码/密钥 |
| 优先级 | 建议使用 P0 / P1 / P2 / P3，定义见第 4 节 |
| 用例类型 | 功能、回归、权限、校验、异常、兼容性、可用性等 |
| 测试层级 | UI、API、集成、端到端、单元等 |
| 测试方法 | 正向、反向、边界、等价类、状态转换、探索式等 |
| 操作步骤 | 可独立执行的有序步骤；复杂步骤可拆到“步骤明细”表 |
| 预期结果 | 每个关键操作对应的可观察、可判定结果 |
| 通过标准 | 明确判定 PASS 的条件，不能只写“功能正常” |
| 后置条件 | 执行完成后的状态、数据清理或保留要求 |
| 自动化状态 | 未自动化、已自动化、自动化不稳定、仅人工等 |
| 关联自动化用例 | 自动化文件、测试方法名或 Playwright TestCaseId |
| 环境 | 测试环境名称、服务地址或部署标识；不要写密码 |
| 浏览器/设备 | 浏览器版本、分辨率、操作系统或设备信息 |
| 版本/构建 | 被测产品版本、构建号或提交版本 |
| 负责人/评审人 | 设计责任人与评审责任人 |
| 设计状态 | 草稿、待评审、已批准、已废弃 |
| 创建日期/更新日期 | 使用 `yyyy-mm-dd` |
| 备注 | 风险、限制、依赖或补充说明 |

### 2.2 步骤明细

当一个用例包含多个动作时，每个动作独立成一行，至少填写：

| 字段 | 填写要求 |
|---|---|
| TestCaseId | 与“用例设计”中的编号一致 |
| 步骤序号 | 从 1 开始，保持连续 |
| 操作/输入 | 页面动作、接口调用或输入值 |
| 步骤测试数据 | 仅记录该步骤使用的数据；敏感数据使用变量名或脱敏占位符 |
| 步骤预期结果 | 该步骤完成后立即可检查的结果 |
| 步骤实际结果 | 执行后回填，不提前填写 |
| 步骤状态 | PASS、FAIL、ERROR、BLOCKED、MANUAL、SKIPPED |
| 步骤截图证据 | 预期/结果截图文件路径或附件引用 |
| 步骤日志/Trace | Trace、控制台日志、网络日志或错误栈路径 |

### 2.3 执行明细

执行时回填，不与设计字段混用：

| 字段 | 填写要求 |
|---|---|
| 执行批次 | 例如 `WEB-REAL-001-20260819-01` |
| 环境、浏览器/设备、版本/构建 | 记录真实执行上下文 |
| 执行人、执行开始、执行结束 | 记录执行责任与时间 |
| 最终状态 | 只能使用项目规定的六种状态 |
| 失败/错误分类 | 测试脚本错误、环境错误、产品失败、定位适配等 |
| 缺陷ID | 只有确认产品结果不符合预期时填写 |
| 实际结果摘要 | 只写真实观察到的结果 |
| 预期截图 | 执行前或关键动作前的基线证据 |
| 结果截图 | 执行完成后的实际页面证据；失败或错误也必须保留 |
| Trace路径、日志路径 | 失败/错误时优先填写，成功时按项目要求保留 |

## 3. 证据规则

1. 每条正式用例至少保留一张预期截图和一张实际结果截图。
2. PASS 不能只依赖代码生成或日志推断，必须有真实执行结果。
3. FAIL 表示真实交互完成，但实际结果不符合预期。
4. ERROR 表示测试脚本、定位、浏览器或执行基础设施错误，不能伪装成产品失败。
5. BLOCKED 表示前置服务、账号、权限或环境缺失，未完成正式验证。
6. 失败和错误应额外保留 Trace、日志、错误栈或网络证据。
7. 截图应优先使用完整页面或完整视口，避免裁剪掉被测控件和结果提示。

## 4. 优先级建议

| 优先级 | 定义 | 系统管理示例 |
|---|---|---|
| P0 | 阻断核心业务或安全边界；失败应停止发布 | 登录、超级管理员权限边界、核心菜单不可访问 |
| P1 | 核心功能；失败会显著影响主流程 | 用户/角色新增、权限分配、菜单访问 |
| P2 | 重要但有替代路径或影响范围较小 | 查询、修改、字典项维护、外部系统配置 |
| P3 | 低风险、展示性或补充性验证 | 文案、排序、非关键样式、低频兼容性 |

## 5. 本项目执行约定

- 正式自动化测试优先使用 Playwright。
- 采用 role、label、test id 和稳定语义定位，不使用固定坐标作为正式定位策略。
- 每条正式自动化测试必须先有 TestCase 记录，并在测试方法、报告、证据目录中保留相同 `TestCaseId`。
- 测试只修改自动化测试仓库；疑似产品问题保留证据并报告，不修改被测产品源码。
- 测试数据使用 `CS` 等专用测试命名；账号密码通过运行环境变量注入，不写入 Markdown、Excel、截图说明或报告。
